# Software-only channel and RIS simulation

This experiment is fully simulated. Candidate channels are abstract alternatives, not specified radio frequencies or measured physical links. The environment generates time-varying direct and RIS-reflected complex channel coefficients, synthetic SNR, packet-success probability, latency, and throughput.

The tabular Q-learning agent selects a candidate channel and one entry in a small virtual RIS phase codebook. If all candidates fall below the simulator's availability threshold, the agent can wait/queue the message. Message priority changes the simulated reward. Flood-risk assessment is not part of the agent's action or reward input.

The main application also connects its generated semantic message to this virtual link. It derives message priority from the selected semantic fields, lets the policy select a candidate/RIS setting, returns a simulated receiver success/failure, and updates the saved Q-table with that feedback. The receiver delivers the complete packet on success; this is an all-or-nothing packet model, not a bit-level semantic decoder.

## Run

From the project directory:

```powershell
.\.venv\Scripts\python.exe evaluate_ris_agent.py
```

After a policy exists, run the complete flood-data-to-simulated-receiver path with:

```powershell
.\.venv\Scripts\python.exe main.py --region region_001
```

Use `--communication-attempts 5` to set the per-message retry limit.

Short run for a quick check:

```powershell
.\.venv\Scripts\python.exe evaluate_ris_agent.py --episodes 25 --eval-episodes 4 --steps 12
```

The evaluator trains Q-learning, then compares it with a greedy best-expected-utility selector and a fixed channel/RIS configuration. It writes `models/ris_q_table.npz` and `data/ris_simulation_results.csv` by default. Adjust training and evaluation episode counts for experiments; a small quick run is only a smoke check, not meaningful performance evidence.

## Simulation assumptions and limits

- All fading, noise/interference changes, availability flags, packet outcomes, throughput, and latency are generated by the simulator.
- The SNR-to-packet-success curve, availability threshold, link budgets, and reward weights are explicit toy assumptions in code. They are not radio standards or calibrated deployment values.
- GOOD/MODERATE/POOR/SEVERE are not used as proof of real connectivity. They describe only simulated SNR ranges.
- Results compare policies under this simulator only. They do not prove performance on a physical RIS, frequency band, or flood-warning network.
- The current flood assessment remains separate. A not-assessed flood state does not stop software communication experiments; use scripted LOW/MEDIUM/HIGH/CRITICAL message priorities as simulation scenarios.
